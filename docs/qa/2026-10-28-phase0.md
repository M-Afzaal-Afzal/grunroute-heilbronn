## Lighthouse, mobile, simulated throttling

| Run | Performance | Accessibility | Best practices | SEO | LCP | TBT |
| --- | --- | --- | --- | --- | --- | --- |
| Main before Phase 0 (production) | 67 | | | | 8.5 s | 80 ms |
| Phase 0 first build (local) | 44 | 97 | 96 | 100 | 10.9 s | 1,590 ms |
| After load changes (local, 2 runs) | 75, 76 | 97 | 96 | 100 | 5.2 to 5.3 s | 220 to 250 ms |
| Production after merge (2 runs) | 64, 70 | 97 | 96 | 100 | 9.3 s | 200 to 240 ms |

The target was 80. It is **not met**. The largest paint is an OpenStreetMap tile. On production the tiles arrive in about 0.6 s in the real trace, but the simulation adds load and render delay as the 710 KB street file and the tree file load right after. Tried and dropped, no gain: preconnect to the tile server, waiting 1 s after the tiles before loading data. Next ideas: smaller `segments.json` (the `raw` block is 2.27 of 6.1 MB, mostly repeated keys), or loading the data in a web worker.

What was done for speed: street data and trees load after the first map tiles (4 s at most), city lines are drawn in chunks of 1,500, the first list keeps the starting view so no second set of tiles loads.
